## 1. Ачивки у аватара

**Приоритет:** последний этап (вместе с п. 2 или сразу после комментариев — на усмотрение, но не раньше остального плана).

**Суть:** После прохождения теста сотрудник получает смайлик или шилдик (achievement badge). Эту ачивку он может отображать возле своего аватара — в углу или поверх иконки.

**Связано с:** Gamification (Фаза 9), quiz_passed signal.

**Требования:**
- При успешном прохождении теста — выдача ачивки
- Возможность выбрать отображение ачивки: в углу аватара или поверх
- Видно в navbar (аватар), в профиле, в комментариях (см. ниже)

## 2. Комментарии с пре-модерацией и HR Task Stack

**Приоритет:** последний этап (вместе с п. 1 — не начинать, пока не закрыт основной план).

**Суть:** Сотрудники могут оставлять комментарии к курсам, статьям или новостям. В опубликованном комментарии видны: никнейм, аватар; опционально ачивка (п. 1), когда она будет сделана.

### Обязательные правила (не обсуждаются)

1. **Публикация только после одобрения HR.** Комментарий в статусе `pending` **никому кроме автора и HR не показывается** как публичный текст. Пока HR не нажал «одобрить», комментарий **не считается опубликованным** (никакого «сначала на сайте, потом модерация» для публичной ленты).
2. **Администрирование обязательно.** Нужен удобный способ для HR обрабатывать очередь: как минимум **Django Admin** (фильтры по `pending`, массовые действия approve/reject) или отдельная HR-страница с тем же смыслом. Без этого фича не считается готовой.
3. **Отклонение:** отклонённый комментарий не отображается публично; при необходимости — уведомление автору (можно второй итерацией).

**HR Task Stack (расширение):** При входе HR видит стек задач на проверку. Реализовать можно в виде оповещений/сообщений. Сначала — модерация комментариев; в тот же стек позже можно добавлять другие дела (например, «прошёл тест — проверить»).

**Требования:**
- Модель Comment (course/article/newspost, user, text, status: `pending` / `approved` / `rejected`, даты/кто модерировал — по желанию)
- UI: форма отправки; для других пользователей — **только одобренные** комментарии
- HR: очередь на модерацию (админка и/или отдельный UI) — см. блок «Обязательные правила» выше
- Уведомления HR о новых `pending` (можно через Фазу 7 Notifications)

## 3. Кандидаты (pre-hire) + конвертация в сотрудника

**Суть:** В систему могут заходить **кандидаты на работу** (ещё не приняты в штат) с **минимальными правами**. Они проходят базовую подготовку и входные тесты. HR мониторит прогресс/результаты и может **конвертировать кандидата в сотрудника** через админку.

**Требования:**
- **Роль/тип пользователя:** `candidate` (кандидат) vs `employee` (сотрудник). Кандидат видит только ограниченный набор разделов/контента.
- **Профиль пользователя:** email, имя, телефон, результаты тестов/баллы.
  - **Телефон нужен всем**, но для кандидата — **обязательный** при регистрации.
- **Ограниченный интерфейс кандидата:** буквально 1–2 раздела:
  - обучение/тестирование
  - упрощённый профиль (редактирование телефона)
- **Флаги видимости контента:** в контенте и тестах добавить поле типа `visible_for_candidates` / `is_candidate_visible`.
  - Курсы/уроки/квизы: можно показывать кандидатам только помеченные сущности.
  - Онбординг: отдельная программа/модули для кандидатов или фильтрация шагов по флагу.
- **Подтверждение email (опционально, но желательно):**
  - при регистрации кандидата отправлять письмо с ссылкой-подтверждением
  - пока email не подтверждён — не пускать в обучение/тесты (или показывать экран “Confirm email”)
- **HR мониторинг:** удобный список кандидатов в админке:
  - статус (кандидат/сотрудник), дата регистрации, последний вход (если есть), прогресс по программе/курсам, результаты тестов (pass/fail/score).
  - фильтры по статусу, источнику, диапазону дат, «сдал/не сдал входной тест».
- **Конвертация кандидата:** действие в админке (кнопка/массовое действие):
  - смена статуса на `employee`, назначение департамента/роли (если нужно), подключение стандартных AssignmentRule (онбординг/курсы).
  - история/результаты тестов кандидата должны сохраняться.

**Вопросы для уточнения (можно позже):**
- Нужна ли **саморегистрация** кандидатов по ссылке-инвайту (token) или просто обычная регистрация?
- Нужно ли удалять/анонимизировать кандидатов через N дней, если не наняли?

**Связано с:** Auth, Onboarding, Courses/Quiz, Admin, Analytics/Notifications.
